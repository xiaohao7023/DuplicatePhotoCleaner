# 需求对齐 Skill

$ARGUMENTS

## 核心原则

**不确定的时候，先对齐，别猜。用画图把抽象变成具体，让对方确认。**

这个 skill 适用于所有类型的需求——UI、架构、功能逻辑。不只是 UI 位置问题。

---

## 什么时候触发

当你读完需求后，发现自己**无法在脑中画出一幅明确的画面**，就说明还没对齐。此时不要动手，进入对齐流程。

典型的"没对齐"信号：
- 你发现自己要在两种实现之间做选择，而选择依据是"我猜用户要的是这个"
- 需求里有模糊词："放下面"、"改一下"、"像那个一样"、"加个东西"
- 你不确定某个东西是 A 还是 B，但你觉得"差不多都行"

---

## 怎么做：画图 → 确认 → 动手

### 1. 把你的理解画出来

用 ASCII 文字图把你的理解具象化。不需要好看，能说清楚就行。

**UI 需求的例子：**
```
页面结构：
┌─────────────────────┐
│  FreeTierCard       │ ← 随滚动消失
├─────────────────────┤ ← 吸顶
│  [Unfavorites | Smart Clean]  │
├─────────────────────┤
│                     │
│  照片网格内容...      │
│                     │
├─────────────────────┤ ← 固定在屏幕底部（悬浮）
│  [Select All] [Delete] │
└─────────────────────┘
```

**流程/逻辑需求的例子：**
```
用户点击 Delete:
  → 是 Pro 用户？
    → Yes → deletePreference == askEveryTime？
      → Yes → 弹确认弹窗
      → No  → 直接删除
    → No  → 还有免费额度？
      → Yes → 走免费删除流程
      → No  → 弹 Paywall
```

**架构需求的例子：**
```
数据流：
  UnfavoritesView  ──写──▶  DashboardUnfavBarState (@Observable)  ──读──▶  DashboardView.floatingBar
```

### 2. 发给对方确认

把画出来的图发过去，问一句话：**"我要做的是这个吗？"**

不需要写很长的解释。图本身就是解释。对方看一眼就能说"对"或者"不对，应该是 XXX"。

### 3. 对方确认后，再动手

只有对方说了 OK，才开始写代码。

---

## "参考 X" 的情况

用户说"参考 X"、"看看 X 怎么做"、"像 X 一样" → **先去看 X 的代码**，看完后把 X 的模式画出来，确认"你要的是和 X 一样的效果吗？"

不要跳过这一步自己设计。

---

## 一句话总结

> **画图花 30 秒，返工花 30 分钟。不确定的时候，画出来问一句。**
